Três regras novas

  • Fila por prioridade de negócio, não por data. Em Execução → Aguardando Aprovação → Em Diagnóstico → Recebida. No mesmo status, quem esperou mais vem antes.
  • Exclusão lógica de Finalizada e Entregue. Somem da fila de trabalho, permanecem no banco para o relatório de tempo médio. Nada é apagado.
  • Aprovação externa por token, sem login. Token único por OS, de uso único e com expiração, entregue por e-mail. Endpoint público — mas só aceita aquele token, para aquela OS, uma vez.
  • Reprovar estorna o estoque. As peças já baixadas voltam. Não é só uma troca de status.

RUN adduser -S spring

Quem cria o bucket do state?

O state do Terraform mora no S3, com lock no DynamoDB. Mas se o próprio Terraform criasse esse bucket, o primeiro apply não teria onde guardar o state do apply que cria o bucket.

O sintoma State em disco morre com o runner

O runner do CI é efêmero. Na execução seguinte o Terraform esqueceria que o bucket existe — e tentaria criá-lo de novo.

A causa Um pré-requisito tratado como recurso

Backend não é aplicação. Bucket e tabela são criados por um script de AWS CLI idempotente — sem state, converge sempre no mesmo lugar, roda dez vezes sem susto.

bootstrap.sh cria a prateleira → S3 + DynamoDB onde o → terraform apply guarda o state
